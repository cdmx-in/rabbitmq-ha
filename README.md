# rabbitmq-ha

Highly available RabbitMQ on Kubernetes: a small Helm chart over the **official RabbitMQ Cluster Operator**.

- 3 brokers, one per node (required pod anti-affinity), spread across zones when available
- `default_queue_type = quorum`: every queue is Raft-replicated and survives loss of one broker
- `pause_minority` partition handling, memory and disk watermarks
- PodDisruptionBudget `maxUnavailable: 1` so node drains never break quorum

Why not the Bitnami chart: it is frozen at RabbitMQ 4.1.3 and its versioned images moved to the
unmaintained `bitnamilegacy` registry (current images are the paid Bitnami Secure Images). The operator
is maintained by the RabbitMQ team, tracks 4.3.x, and handles rolling upgrades and scaling.

## Install from Rancher

1. Prerequisites (once per cluster): cert-manager (often already present on Rancher-managed clusters;
   otherwise install it from https://charts.jetstack.io) and the RabbitMQ Cluster Operator. For the operator use Cluster → Import YAML with
   `https://github.com/rabbitmq/cluster-operator/releases/download/v2.23.0/cluster-operator.yml`
   or `kubectl apply -f` that URL.
2. Apps → Repositories → Create → Target: **http(s) URL** → `https://cdmx-in.github.io/rabbitmq-ha`
3. Apps → Charts → **RabbitMQ HA** → Install. The form exposes brokers, storage class, size, resources
   and service type; everything else is in the values YAML tab.

Helm equivalent:

```bash
helm repo add rabbitmq-ha https://cdmx-in.github.io/rabbitmq-ha
helm upgrade --install rmq rabbitmq-ha/rabbitmq-ha -n rabbitmq --create-namespace -f values-prod.yaml
```

## Install from source

```bash
kubectl apply -f https://github.com/cert-manager/cert-manager/releases/download/v1.21.2/cert-manager.yaml
kubectl apply -f https://github.com/rabbitmq/cluster-operator/releases/download/v2.23.0/cluster-operator.yml
helm upgrade --install rmq ./charts/rabbitmq-ha -n rabbitmq --create-namespace -f values-prod.yaml
```

Admin credentials are generated by the operator:

```bash
kubectl -n rabbitmq get secret rmq-default-user -o jsonpath='{.data.username}' | base64 -d
kubectl -n rabbitmq get secret rmq-default-user -o jsonpath='{.data.password}' | base64 -d
```

In-cluster endpoint: `rmq.rabbitmq.svc.cluster.local:5672` (AMQP), `:15672` (management).
Create a dedicated least-privilege user for applications instead of `default_user` before go-live.

## Files

| Path | Purpose |
|---|---|
| `charts/rabbitmq-ha/` | Helm chart: `RabbitmqCluster` CR + PodDisruptionBudget |
| `values-prod.yaml` | production example (ClusterIP, pinned image, SSD storage) |
| `values-kind.yaml` | local rehearsal values (NodePort, small resources) |
| `kind.yaml` | 4-node kind cluster for local testing |

## Local rehearsal

```bash
kind create cluster --config kind.yaml
# install cert-manager + operator as above, then:
helm upgrade --install rmq ./charts/rabbitmq-ha -n rabbitmq --create-namespace -f values-kind.yaml
# AMQP localhost:5673, management UI http://localhost:15673
```

Failover test: publish continuously, then `kubectl -n rabbitmq delete pod <leader> --grace-period=0 --force`.
Expected: leader re-elected in a few seconds, no publish failures, unacked messages redelivered
(at-least-once, so consumers must be idempotent), pod rejoins the cluster.

## Not yet tested

- Node loss (only pod deletion was exercised), rolling image upgrades, and network partitions.
- Rancher UI install itself; the repo index and `questions.yaml` follow Rancher's documented format.

## Notes for clients

- Declare queues on the broker side (management API or the Messaging Topology Operator `Queue` CRD)
  rather than relying on clients to create them.
- Quorum queues are the default here; no `x-queue-type` argument is needed on the client.
